## 1. What triggered this gate

`feature/evidence-service` modifies 18 historical migration files (in addition to adding 3 genuinely new ones for the Evidence Service schema). These edits were made by porting fixes discovered while replaying the full migration chain against a clean, disposable database in isolated CI — a technique that reliably surfaces migrations that fail on a *fresh* database, but says nothing on its own about whether the *same* fix is needed against the database that's actually running in production, which has its own real, linear history that a fresh replay does not reproduce.

The prior Phase 0 audit ([the "First Response"](../.)) flagged this as the central blocker. This document resolves it as far as available evidence allows and names exactly what's left.

## 2. Classification taxonomy applied

Every one of the 18 files received exactly one primary classification:

| Classification | Count | Meaning |
|---|---|---|
| `REPLAY_COMPATIBILITY_ONLY` | 10 | Production already has (or very likely has) the equivalent end state through its own real history; the edit exists only so a *reconstructed* database can replay cleanly. |
| `REQUIRED_FORWARD_FIX` | 5 | Genuine, unresolved doubt that production has the desired state — a new forward migration is likely needed, pending confirmation. |
| `ALREADY_PRODUCTION_APPLIED_DIFFERENTLY` | 4 | Production has the state via a real, out-of-band path (manual SQL, a since-abandoned earlier migration) — documented as such rather than pretending the edited historical file produced it. |
| `ACCIDENTAL_MUTATION` | 1 | The edit's own cited justification could not be verified against repository evidence. |
| `UNSAFE_HISTORY_REWRITE` | 1 | Genuine ambiguity about what production actually has, combined with the edit silently changing observable behavior (an error becomes a silent skip) — too risky to accept on replay-passing alone. |

Full reasoning, evidence, and required next action for every file is in [MIGRATION_CLASSIFICATION.json](MIGRATION_CLASSIFICATION.json).

## 3. Four findings that matter more than the general gate

Ranked by severity, independent of whether Evidence Service ever merges:

### 3.1 `is_service_role()` may still be exploitable in production (finding #2, P0-candidate)

Migration `20260112065039` replaces a role-check function whose old logic — proven exploitable *this session* in the isolated CI replay (a non-admin authenticated caller got treated as `service_role`, reading another user's referral stats) — depended on a Postgres session GUC that a connection pooler can set independently of the caller's actual identity. If this migration filename was already recorded as applied in production, **editing the historical file has zero effect on the live function** — `CREATE OR REPLACE FUNCTION` only executes when the migration actually runs, and Supabase's CLI tracks migrations by filename, not content. Production's `is_service_role()` may right now still contain the exploitable branch.

**This needs direct confirmation before anything else in this gate**, independent of Evidence Service timing.

### 3.2 `subscription_upsert_fix.sql` may have silently failed entirely in production (finding #9, P0-candidate)

Migration `20260608000002` ends with a bare top-level `RAISE NOTICE`, which is invalid outside a PL/pgSQL block (`42601`). Postgres runs each migration file as one transaction by default — if this syntax error fired in production the way it fired in this session's CI replay, **the entire file rolled back**, including a unique constraint on `subscriptions` and an `admin_fix_subscription` RPC defined earlier in the same file. Billing-adjacent; this master prompt's own Section J treats this class of gap as release-blocking on its own terms.

### 3.3 Phase D scenario-ledger tables likely do not exist in production (finding #16, P0-candidate, highest confidence of the four)

Migration `20260730084255` unconditionally `CREATE TABLE public.scenarios` — but `public.scenarios` already existed from an earlier migration (`20260308082036`) with a completely different, flat Monte-Carlo shape. The collision aborts the whole transaction, meaning `scenario_sets` (created earlier in the same file) never actually gets created either, and `scenario_versions`/`scenario_runs` (later in the file) never get reached at all.

**This is CODE_VERIFIED, not just inferred**: `src/integrations/supabase/types.ts` confirms `public.scenarios` still has the old flat shape (`params`/`output`/`monte_carlo_result`/`confidence_score`/`scenario_type`) today, and `scenario_sets`/`scenario_versions`/`scenario_runs` are entirely absent from the generated types. A prior session in this same project reported "Phase D-14: live verification" as complete for this exact feature. If this finding holds, the entire Scenario Workspace feature — `create-scenario-set`, `run-scenario`, `promote-scenario`, `scenario-breakpoint` edge functions, and the UI — has had no real table to write to since it shipped, and any customer who used it needs data-impact assessment.

The proposed fix (rename the legacy table, non-destructively) touches live production data and explicitly requires your review before it's ever applied — I have not applied it and will not without your go-ahead.

### 3.4 `benchmark_master_geo` may have zero rows in production (finding #8, P1-candidate)

Migration `20260608000001`'s original seed INSERT never supplied a value for `sector_level1`, which `types.ts` confirms is `TEXT NOT NULL` with no default. If that constraint was already in place when this migration first ran in production, the insert would have failed there too — meaning the geography cost-multiplier table this master prompt's Section 2.1 numeric-ownership rules ultimately feed from may be empty in production right now.
