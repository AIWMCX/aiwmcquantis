# Evidence packet fixtures — manual quality review

Generated by `scripts/evidence-service/generate-fixtures.ts`, which runs the
**real** pipeline (`runEvidencePipeline`) end to end — no hand-authored JSON.
No `TAVILY_API_KEY` was available in this environment, so the Tavily HTTP
call is mocked with realistic (hand-written, clearly fictional) result data;
every fixture's `_fixtureMeta.dataSource` says so explicitly. Set
`TAVILY_API_KEY` and `EVIDENCE_PROVIDER_INTEGRATION_TESTS=true` and re-run
the script to regenerate against the live API.

## What's genuinely working (verified by inspecting the output)

- **URL normalization + dedup/independence clustering** — real, and doing
  its job: `saas-startup-austin.json`'s two SaaS-benchmark sources cluster
  as independent (different content hash → `sourceIndependenceCount: 2` →
  `SUPPORTED`), while the single-source claims correctly land on
  `SINGLE_SOURCE`, not `SUPPORTED`.
- **Genuine "no evidence found" handling** — the SaaS fixture's regulation
  question deliberately returns zero mock results, and the pipeline
  correctly records it in `unresolvedQuestions` rather than fabricating a
  claim.
- **Content hashing** — every `contentHash` is a real, verified 64-char
  SHA-256 hex digest computed over the actual passage text.
- **Freshness classification** — now populated from `publishedAt` (see
  below; this was fixed during this review, not left as the original gap).
- **Privacy gate** — proven at the pipeline-test level, not just here: a
  raw email embedded in the business idea never reaches the query sent to
  Tavily.
- **Storage policy conservatism** — every source correctly carries
  `storagePolicy: METADATA_ONLY`, matching the real, cited finding in
  `provider-registry.ts` that Tavily's ToS doesn't address result caching.

## Known, honest gaps (found during this manual review, not fixed yet)

1. **`sourceType` is always `OTHER`.** No real classification exists yet
   to recognize `bls.gov` as GOVERNMENT/OFFICIAL, `costar.com` as INDUSTRY,
   `denvergov.org` as GOVERNMENT, etc. This is the most visible quality
   gap in these fixtures — a genuinely missing capability (Source Lens
   classification, master prompt section 8), not a bug. Worth prioritizing
   in a follow-up slice: even a simple domain-suffix/allowlist heuristic
   (`.gov` → GOVERNMENT, a short list of known industry-data domains →
   INDUSTRY) would meaningfully improve on `OTHER` for every source.

2. **Claim statements are template strings** (`"Evidence gathered for: X"`),
   not synthesized summaries of what the sources actually say. Already
   documented as a deliberate limitation in `pipeline.ts`'s header — real
   claim-statement synthesis needs either an LLM step or an entailment
   model, neither of which exists in this slice.

3. **`primaryStatus` is always `UNKNOWN`.** No logic distinguishes a
   primary source (e.g. the BLS page itself) from a secondary one (e.g. a
   blog quoting the BLS page). Same root cause as #1 — needs the same kind
   of classification work.

4. **Every claim in this slice is `SUPPORTED` or `SINGLE_SOURCE`, never
   `CONTESTED`.** This is a real, structural limitation, not a fixture
   artifact: `pipeline.ts` marks every retrieved source as `SUPPORTS`
   because there's no entailment/contradiction-detection step. The
   contradiction path is fully built and independently tested
   (`evidence-graph.test.ts`'s section-30 test), it just has no caller
   from this pipeline yet.

None of these four are silent — each is called out in `pipeline.ts`'s own
header comment or `provider-registry.ts`'s citation, and none of them
block E5 (persistence): the `QuantisEvidencePacket` shape these fixtures
produce is exactly what E5's schema should be designed against, gaps and
all — persistence doesn't need claim quality to be perfect, it needs the
*shape* to be real, which it now is.
