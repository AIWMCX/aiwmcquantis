# Dahl Canary Rollout — Status & Re-enablement Criteria

GTM-audit item #21 (2026-08-27, Category 05): this document exists
because it didn't before. A re-enablement bar ("a production-sized
fixture must pass N times running in Preview") had been referenced
conversationally across sessions but was never committed anywhere in
the repo — a real-code investigation on 2026-08-27 searched `docs/`,
every Dahl-touching PR, and every code comment and found no trace of it.
That ambiguity is itself the bug this doc fixes: from now on, "has the
bar been cleared" should be answerable by reading this file plus the
two data sources it points to, not by searching chat history.

## What Dahl is

An alternative inference provider (`supabase/functions/_shared/dahl-adapter.ts`)
to the existing Anthropic/DeepSeek path, integrated behind a two-gate
canary system (`supabase/functions/_shared/dahl-canary.ts`, gated in
`llm-call.ts`'s `aiCall()`). `DAHL_ENABLED` is the master switch;
`DAHL_CANARY_MODE` (`off` / `admin_only` / `percent`) controls who's
actually eligible. Both gates fail closed — any missing/malformed
config, or a request with no stable identity to bucket, resolves to
**not eligible**, never to "eligible by default."

## The 2026-08-24 incident, in one sentence

Dahl could return a response that succeeded at the transport level but
didn't parse as valid JSON, silently degrading a real analysis to the
deterministic-only fallback with no visible error. `DAHL_CANARY_MODE`
was set to `off` the same day as containment. The JSON-repair mechanism
(`dahl-adapter.ts`'s `extractJsonSafely`/`repairJsonViaDahl`) and the
two-phase `ai_calls` telemetry (`pending`/`completed`/`failed` status,
`retry_count`, `repair_attempted`) that would let anyone verify the fix
both shipped afterward (PR #82, then PR #85, merged 2026-08-25).

## Rollout stages

| Stage | `DAHL_CANARY_MODE` | Who's eligible |
|---|---|---|
| 0 — Contained (current) | `off` | Nobody |
| 1 — Internal validation | `off`, but manual smoke tests run | Nobody (no real traffic) |
| 2 — Admin canary | `admin_only` | Only UUIDs in `DAHL_CANARY_ADMIN_USER_IDS` |
| 3 — Small rollout | `percent`, `DAHL_CANARY_PERCENT` low (e.g. 5) | A stable, deterministic slice of real users |
| 4 — Expand | `percent`, increasing | Larger slice |
| 5 — Full | `percent=100` (or `DAHL_ENABLED` alone, once `percent` is redundant) | Everyone |

## Advancement criteria

Each stage advances only when the stage below it has cleared its bar —
never skip a stage, and a failure at any stage means dropping back to
`off`, not holding in place.

**Stage 0 → 1 (start validating again):** run
`.github/workflows/dahl-smoke-test.yml` manually (`workflow_dispatch`).
This is safe to run at any time — per its own header comment, it never
touches `DAHL_ENABLED`/`DAHL_CANARY_MODE` and routes no real user
traffic; it only proves `DAHL_API_KEY` is live and exercises the real
adapter code (`scripts/dahl-smoke-test.ts`,
`scripts/dahl-json-mode-probe.ts`) against the exact request shape that
caused the original incident.

**Stage 1 → 2 (`off` → `admin_only`):**
- The smoke test workflow must pass **3 consecutive manual runs**, on
  **at least 2 different days** (not 3 runs back-to-back in one sitting
  — the point is confirming stability over time, not just this instant).
- Zero JSON-parse failures across those runs. A repair-required-but-
  succeeded call is fine (that's the repair mechanism working as
  designed); a call that still comes back unparseable after repair is
  not.
- Check current status any time via:
  ```bash
  gh run list --workflow "Dahl Smoke Test (manual)" --limit 10 --json createdAt,conclusion
  ```

**Stage 2 → 3 (`admin_only` → `percent`, low):**
- At least **20 real `ai_calls` rows** with `provider` indicating Dahl,
  generated by real admin-account usage (not the smoke test), with:
  - Zero rows stuck in `pending` past a reasonable window (see
    `scripts/check-stuck-ai-calls.ts` — if this ever flags a Dahl row,
    that's an automatic hold, not just a data point).
  - `repair_attempted = true` rate not meaningfully higher than the
    non-Dahl baseline for the same task type (a repair rate climbing
    over time within this stage means the underlying parse-failure
    class isn't actually fixed, just being papered over).
- Check via:
  ```sql
  SELECT status, repair_attempted, COUNT(*), MIN(created_at), MAX(created_at)
  FROM public.ai_calls
  WHERE provider ILIKE '%dahl%'
  GROUP BY status, repair_attempted
  ORDER BY MAX(created_at) DESC;
  ```

**Stage 3 → 4 → 5 (expanding `percent`):**
- No `stuck-ai-calls-check.yml` alert firing for Dahl rows during the
  current percentage's soak period (recommend at least 72 hours per
  step, not a fixed call count — real traffic patterns vary by day of
  week).
- Failure/repair rates at the current percentage no worse than the
  previous stage's — a step up should never look worse than the step
  it came from.

## Current state (as of 2026-08-27)

Confirmed live, not assumed:

- `DAHL_ENABLED=true`, `DAHL_CANARY_MODE=off`, `DAHL_CANARY_PERCENT=0`
  (production GitHub environment variables, last changed
  2026-08-24T15:38:18Z — the incident containment).
- The smoke-test workflow has run **3 times total, ever**, all on
  2026-08-24, all **before** the JSON-repair fix merged that same day.
  Zero runs since.
- `ai_calls` has **3 Dahl rows total, ever** (2 `completed`, 1
  `failed`), all from 2026-08-24, all predating the `repair_attempted`
  column (added 2026-08-25). Zero Dahl activity of any kind in the 3
  days since the fix shipped.

**Verdict: still at Stage 0. The fix is real and shipped, but has never
been exercised even once since — there is no data yet to evaluate,
because nothing has generated any.** The next concrete action is simply
running the smoke test workflow to get the first real post-fix data
point (Stage 1), not re-enabling the canary directly.
